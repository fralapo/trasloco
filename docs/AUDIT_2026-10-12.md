# Trasloco 2.0 — second engineering and safety audit

Date: 2026-10-12. Review scope: `hardening/production-readiness-2026-10`, compared with published `main`. This is an engineering audit, **not** a certification or a production-release approval.

## Review method

Inspected the PHP import/export and extractor paths, manifest verification, scheduling, background-worker leases and mutex, backup listing/retention, REST authorization, encryption, WordPress/MySQL integration fixtures and CI. Applied [the project engineering playbook](ENGINEERING_WORKFLOW.md) (impact analysis, security review, regression tests, verification). Relevant WordPress source-of-truth documentation:

- [WP-Cron recurring events](https://developer.wordpress.org/reference/functions/wp_schedule_event/)

## Implemented during this audit

| Severity | Finding | Remediation | Regression |
|---|---|---|---|
| Critical | Automated retention could delete a pre-restore or pre-upgrade recovery snapshot | Recovery snapshots now carry a durable `recovery-` filename prefix; both WP-CLI and cron retention exclude them | A subsequent retention=1 backup must preserve the recovery point |
| High | Changing the frequency left a stale WP-Cron recurrence | Detect `wp_get_schedule` mismatch and clear/reschedule | Daily → weekly → daily → disabled |
| High | Reusing an idempotency key for different archives/operations incorrectly returned the previous job | Compare kind and serialized payload; refuse a conflict with 409 | Cross-archive and cross-kind collision |
| Critical | Archive extraction accepted on-disk symlink components beneath otherwise safe relative paths | Validate all existing destination path components before `mkdir/fopen`; reject symlinks in full and selective extraction | Synthetic malicious .wpress attempting to write outside root |
| High | Local backup restore trusted a structurally valid archive even if its sidecar checksum differed | Validate existing SHA-256 sidecar before beginning the destructive restore | Corrupted local archive must fail before changing destination |
| High | Server-side backup and recovery workers could export concurrently | Nonblocking filesystem `flock` mutex; fail closed instead of competing | Simulated overlapping export |
| High | Long exports could be abandoned despite progress; immediate lease renewals falsely failed on unchanged MySQL row values | Periodic progress-based renewal plus monotonic `lease_until` update | Owned lease extension and same-second renewal |
| Low | Scheduled cron and queued background hooks survived plugin deactivation | Unschedule on plugin deactivation; retain archive/job history | WP-CLI deactivate and verify absent cron hooks |

Every listed implementation is still subject to current branch CI verification. A completed unit test is not equivalent to real-hosting acceptance.

## Remaining risks — prioritize before production release

### P0: data loss or compromised recovery
1. **Independent disaster recovery:** recovery points are backup archives, not automatic rollback. WordPress or the database can be unavailable after a partial import. Build and test an independent restore bootstrap with safeguards and documented operator recovery.
2. **Restore atomicity and consistency:** MySQL DDL and file overwrites are not a single transaction. Design staged file replacement, a recoverable SQL strategy, stop-write/maintenance windows, and injected failure restoration tests.
3. **Symlink race in hostile local hosting:** path-component checks reject pre-existing symlinks but a process with write access can replace a component between check and fopen. Harden hosting trust boundaries and evaluate OS-level directory-relative access APIs rather than promising full containment.
4. **Nginx and reverse proxy storage protection:** Apache/IIS rules are not sufficient for Nginx. Require a private out-of-docroot backup path or explicit Nginx deny configuration, and test access anonymously over real HTTP.

### P1: operational reliability
5. **Durable byte-level resumability:** a persistent job record does not yet resume an interrupted backup at its previous file byte or SQL row; implement idempotent checkpoints, segment verification, and crash-replay tests before promising resume.
6. **Cross-operation serialization:** the new mutex protects local server-side backup workers. Interactive AJAX export/import, shared/multi-server deployments and remote storage need shared coordination and trustworthy leases.
7. **Consistency with online databases:** backups taken while WooCommerce/HPOS or other transactional plugins write may be inconsistent. Add supported maintenance/snapshot strategies and targeted HPOS/multisite test fixtures.
8. **Robust backup verification:** SHA-256 sidecars detect changed bytes but do not authenticate an adversarial replacement of both archive and manifest. Add signed/versioned origin metadata and independent restore rehearsal.
9. **Performance and bounded work:** currently hashing a very large archive may exceed hosting request limits; use resumable chunk digests and server-side cron/queue workers. Do not treat a progress bar as durable continuation.
10. **True remote storage:** the local stream adapter is not a production-ready S3/R2/B2/SFTP/WebDAV or OAuth connector. Implement provider-specific upload/download verification, retries, quotas, key rotation and revocation.

### P2: product maturity
11. Add browser E2E coverage (including accessible keyboard workflows) for scheduling, uploading and recovery, with screenshots on failure.
12. Complete release compatibility matrix: PHP 7.4–8.4, WordPress current/previous, MySQL and MariaDB, Apache/Nginx/IIS, large archives, multisite, WooCommerce HPOS.
13. Complete encrypted archive admin UX, key recovery policy and fail-closed treatment of decrypted temporary files.
14. Complete selective SQL/data restore, checksum diff, direct migration, incremental chain pruning, staging and agency dashboard only when their foundational consistency and security gates pass.
15. Expose an honest product-facing status for backup age, successful **restore** rehearsal and unknown verification state; never describe “manifest present” as “verified”.

## Release rule

Do not merge [PR #1](https://github.com/fralapo/trasloco/pull/1) into `main` merely because syntax and the current single-site integration pass. Require verified disaster recovery, browser workflows, Nginx behavior and cross-host/large archive cases appropriate for a production migration tool. Keep unsupported features in the roadmap instead of representing them as implemented.
